# Методология проектирования атомарных агентов

## Философия: два встречных потока

### Проблема одного потока

**Чистый bottom-up**: строишь атомы, но не знаешь, к чему они должны сложиться. Россыпь полезных мелочей, которые не стыкуются. Атомы есть — архитектуры нет.

**Чистый top-down**: рисуешь красивую карту из 5 стадий, но не знаешь реальных ограничений. Проектируешь агентов, которые на практике не работают. Архитектура есть — фундамента нет.

### Два потока одновременно

```
TOP-DOWN (карта)                    BOTTOM-UP (территория)

Зачем? Цель/Процесс                Что болит? Ручная операция
       ↓                                    ↓
Какие стадии?                       Что реально автоматизируемо?
(Input→Process→Context→             (попробовал — получилось / нет)
 Output→Review)                             ↓
       ↓                            Какие реальные ограничения?
Какие слоты нужны?                  (формат, качество, скорость)
       ↓                                    ↓
       └──────────► КОНТРАКТ ◄──────────────┘
                   (Agent Card)
                       ↓
                   ОБРАТНАЯ СВЯЗЬ
                   ↙          ↘
          Обновить карту    Уточнить атом
```

**Top-down** отвечает: **ЧТО должно существовать** — карта процесса, стадии, слоты, интерфейсы.

**Bottom-up** отвечает: **ЧТО реально работает** — реальные ограничения, форматы, скорость.

**Контракт (Agent Card)** — точка встречи двух потоков.

## DIKW как вертикальная ось трансформации

```
WISDOM    ─── Решения, принципы, "когда НЕ делать"
  ↑           (Review/Reflection)
KNOWLEDGE ─── Контекстуализированное понимание
  ↑           "я знаю как это связано с моими целями"
  ↑           (Context/Memory)
INFORMATION ─ Структурированные, отфильтрованные данные
  ↑           "я знаю что здесь важно"
  ↑           (Processing/Analysis)
DATA      ─── Сырой поток: ссылки, тексты, сигналы
              (Input/Capture)
```

### Правило одного перехода

> **Атомарный агент выполняет ОДИН переход DIKW. Не два. Не три. Один.**

- `D→I` — сборщик (собрал сырьё, структурировал)
- `I→K` — аналитик (связал с контекстом, нашёл паттерны)
- `K→W` — советник (сделал вывод, предложил действие)

Если агент прыгает `D→K` — это два агента. Если `D→W` — три.

### DIKW-матрица процесса

```
              Input/      Processing/   Context/     Output/      Review/
              Capture     Analysis      Memory       Action       Reflection
            ┌───────────┬─────────────┬────────────┬────────────┬────────────┐
  Wisdom    │           │             │            │ Формирует  │ Оценивает  │
  (W)       │           │             │            │ решение    │ решение    │
            │           │             │            │ [K→W]      │ [W→W']     │
            ├───────────┼─────────────┼────────────┼────────────┼────────────┤
  Knowledge │           │             │ Связывает  │            │            │
  (K)       │           │             │ с целями   │            │            │
            │           │             │ [I→K]      │            │            │
            ├───────────┼─────────────┼────────────┼────────────┼────────────┤
  Informati-│           │ Фильтрует,  │            │            │            │
  on (I)    │           │ структури-  │            │            │            │
            │           │ рует [D→I]  │            │            │            │
            ├───────────┼─────────────┼────────────┼────────────┼────────────┤
  Data      │ Собирает  │             │            │            │            │
  (D)       │ сырьё     │             │            │            │            │
            │ [→D]      │             │            │            │            │
            └───────────┴─────────────┴────────────┴────────────┴────────────┘
```

## Kolb как цикл обучения проектировщика

Kolb работает не внутри агента, а вокруг — как ты учишься проектировать лучше:

```
1. CONCRETE EXPERIENCE (CE)
   Построил атом. Запустил. Получил реальный результат.
        ↓
2. REFLECTIVE OBSERVATION (RO)
   Что получилось? Что нет? Где агент "поплыл"?
   Выход подошёл следующему агенту?
        ↓
3. ABSTRACT CONCEPTUALIZATION (AC)
   Извлечь принцип / паттерн.
   "PDF-парсинг — отдельный агент"
   "D→I нельзя совмещать с I→K"
   Обновить Process Map.
        ↓
4. ACTIVE EXPERIMENTATION (AE)
   Применить обновлённую модель.
   Перепроектировать? Разделить? Построить следующий?
        ↓
   (→ CE нового цикла)
```

### Kolb + DIKW: спиральная динамика

Каждый полный оборот Kolb поднимает тебя по DIKW как проектировщика:

- **Цикл 1 (DATA):** построил первый атом, увидел что работает
- **Цикл 2-3 (INFORMATION):** построил несколько, увидел паттерны стыков
- **Цикл 4+ (KNOWLEDGE→WISDOM):** знаешь не только КАК, но и КОГДА и ЗАЧЕМ

## 5 фаз проектирования

| Фаза | Действие | DIKW | Kolb |
|------|----------|------|------|
| **1. MAP** | Нарисовать карту процесса. Разметить DIKW-уровни | Разметка матрицы | — |
| **2. GROUND** | Выбрать слот + конкретную боль. Попробовать вручную | — | CE |
| **3. CONTRACT** | Вход/выход. Вход = уровень X, выход = X+1 по DIKW | Один переход | — |
| **4. VALIDATE** | 3 примера + проверка стыков с соседями | — | RO |
| **5. FEEDBACK** | Извлечь принцип. Обновить карту. Выбрать следующий атом | Обновление | AC + AE |

## Тест на атомарность (8 вопросов)

| # | Вопрос | Если "нет" → |
|---|--------|-------------|
| 1 | Одно предложение, один глагол? | Разбей |
| 2 | Если разделить — каждая часть полезна? | Уже атомарный |
| 3 | Нужна условная логика по типу входа? | Разбей |
| 4 | Можно проверить по 3 примерам? | Уточни границы |
| 5 | Выход одного типа? | Разбей по типам |
| 6 | Один DIKW-переход? (D→I, I→K, или K→W) | Разбей по уровням |
| 7 | Вход и выход на соседних DIKW-уровнях? | Прыжок — разбей |
| 8 | Можешь назвать DIKW-уровень входа и выхода? | Не определён — уточни |

## Принципы

1. **Contract-first** — вход/выход до реализации
2. **One DIKW transition** — один переход, не больше
3. **3-example validation** — без прогона 3 примеров агент не спроектирован
4. **Explicit boundaries** — "чего НЕ делает" обязательно
5. **One verb rule** — два глагола в purpose = два агента
6. **Composability by default** — upstream и downstream всегда определены
7. **Living card** — Kolb Journal превращает карточку в эволюционирующий артефакт
8. **Map updates** — каждый построенный атом может изменить карту процесса

## Режимы работы

**Режим A: "У меня есть задача"** — пользователь приходит с конкретной болью. Провести через 5 фаз, выдать Agent Card.

**Режим B: "У меня есть процесс"** — пользователь приходит с большим процессом. Сначала MAP (декомпозиция на стадии + DIKW-разметка), потом проектирование Agent Card для каждого слота, потом карта связей.
